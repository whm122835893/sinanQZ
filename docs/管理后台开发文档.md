## 1. 总体方案

### 1.1 与提示词的差异修订

提示词按"独立 NestJS 后端 + TypeORM + code=200 响应码"编写，与本仓库现状不符。本文档保留提示词全部业务规则与功能清单，技术落地按下表修订，其余内容（库存闭环、资格购/优先购、17 模块、权限矩阵、高风险操作规范）原样继承。

| 编号 | 提示词原文 | 本文档修订 | 理由 |
| --- | --- | --- | --- |
| D-1 | 管理后台后端为独立 NestJS 项目 | 复用现有 ThinkPHP 8 后端，以多应用模式新增 `app/admin/` 应用 | 复用 Db 层、公共函数、JWT 库与部署方式，避免双栈分裂；已与需求方确认 |
| D-2 | 响应 `code === 200` 为成功 | 沿用现有 `{code:0, message, data}` | 与 C 端共享 `JsonResponse` trait，前端拦截器统一判断 `code === 0` |
| D-3 | `nft_blind_boxes` 独立拥有 edition/sold/circulate 等库存字段 | 保持"盲盒 = 藏品行 + 1:1 扩展行"模型，库存字段即该藏品行的 edition/sold/locked/circulate，新增 destroyed_count/airdropped_count/reserved_count 加在藏品表，盲盒行自动继承 | 现有模型已通过 C 端联调验证；盲盒行是独立藏品行，语义上仍是"独立库存"，仅物理位置不同 |
| D-4 | 抽奖奖品类型不含积分 | 保留 `points`（司南币）作为奖励类型之一 | C 端钱包有司南币体系且抽奖奖池已使用；其余活动奖励类型按提示词统一扩展 |
| D-5 | 数据库迁移用 TypeORM migration | 纯 SQL 迁移脚本 `database/migrations-admin/*.sql`，幂等可重跑 | 与现有 init.sql 交付方式一致 |
| D-6 | 表述"42 张现有表" | 实际现有 33 张表，其中 9 张需扩展、24 张需新增 | 以本仓库 init.sql 实测为准 |

### 1.2 建设范围

按提示词 17 个模块全量规划，实施分五期（见第 12 章），本期先交付 P0+P1：

- 后端：`/admin/api/v1/` 路由组 209 个接口（19 个模块分组，见第 8 章），独立管理员 JWT，5 角色 RBAC，全量审计日志。
- 前端：`sinan-admin/` 独立工程（Vue 3 + TS + Element Plus + ECharts），视觉遵循 C 端"司南红 + 金 + 云雷纹"设计语言（见第 3 章）。
- 数据库：9 张表扩展 + 24 张新表。
- C 端联动：优先购/资格购校验、寄售与转赠开关、限价、藏品级限购等 6 处接口改造（见第 10 章）。

## 2. 系统架构

### 2.1 部署拓扑

```
                     ┌──────────────────────────────────────────┐
                     │              MySQL  sinan_nft             │
                     │   33 张业务表（C 端在用） + 24 张管理新表  │
                     └────────▲───────────────────▲───────────┘
                              │                   │
              ┌───────────────┴────┐    ┌──────────┴────────────┐
              │  sinan-nft-backend │    │  sinan-nft-backend    │
              │  /api/*   (C 端应用)│    │  /admin/api/v1/*      │
              │  app/      用户JWT  │    │  app/admin/  管理员JWT │
              │  :8000            │    │  :8000（同进程多应用）   │
              └────────▲───────────┘    └──────────▲────────────┘
                       │                           │
              ┌────────┴─────────┐      ┌──────────┴──────────┐
              │ jichao-art-source │      │     sinan-admin      │
              │ C 端 H5 :5173     │      │ 管理后台 PC :5174    │
              └───────────────────┘      └─────────────────────┘
```

要点：

- 同一 PHP 进程内启用 ThinkPHP 多应用（`composer require topthink/think-multi-app`），新建 `app/admin/` 应用目录，与现有 `app/controller`（默认应用）完全隔离；C 端路由零改动。
- 管理端前端为独立 Vite 工程，独立端口、独立登录态，生产环境经 Nginx 分别反代 `/admin` 与 `/api`。
- 管理员 JWT 与用户 JWT 使用不同密钥、不同 token claim，中间件互不通用，杜绝越权串用。

## 4. 数据库设计

命名与现有库对齐：`nft_` 前缀、snake_case、`DATETIME(3)`、内容表带 `deleted_at` 软删除、每字段 COMMENT、`utf8mb4_unicode_ci`。所有新表不设强外键的除外说明见各表。

### 4.1 现有表扩展（9 张）

#### 4.1.1 `nft_collectibles`（藏品主表，盲盒行同样适用）

```sql
ALTER TABLE `nft_collectibles`
  ADD COLUMN `release_quantity` INT UNSIGNED NULL DEFAULT NULL COMMENT '计划发售数量，NULL=不限（以库存池售完为止）' AFTER `edition`,
  ADD COLUMN `reserved_count`   INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '配额预留总数（优先购/活动空投/签到/邀请/抽奖等，冻结自库存池）' AFTER `locked_quantity`,
  ADD COLUMN `airdropped_count` INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '已独立空投数量' AFTER `reserved_count`,
  ADD COLUMN `destroyed_count` INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '已销毁数量（不可逆）' AFTER `airdropped_count`,
  ADD COLUMN `is_transferable`  TINYINT(1)  NOT NULL DEFAULT 1 COMMENT '是否可转赠 1=可 0=不可（藏品级独立开关）' AFTER `tag`,
  ADD COLUMN `is_resaleable`    TINYINT(1)  NOT NULL DEFAULT 1 COMMENT '是否允许寄售（二级市场总开关，关闭时强制下架全部挂单）' AFTER `is_transferable`,
  ADD COLUMN `resale_price_mode` TINYINT     NOT NULL DEFAULT 0 COMMENT '寄售价格管控 0=不限价 1=限价' AFTER `is_resaleable`,
  ADD COLUMN `resale_price_min` DECIMAL(10,2) NULL DEFAULT NULL COMMENT '寄售限价下限（元）' AFTER `resale_price_mode`,
  ADD COLUMN `resale_price_max` DECIMAL(10,2) NULL DEFAULT NULL COMMENT '寄售限价上限（元）' AFTER `resale_price_min`,
  ADD COLUMN `per_user_limit`   INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '藏品级每人限购，0=不限购；非 0 时覆盖系统配置 purchase_limit_per_user' AFTER `resale_price_max`;

ALTER TABLE `nft_collectibles`
  MODIFY COLUMN `status` ENUM('draft','upcoming','onsale','soldout','off')
  NOT NULL DEFAULT 'draft' COMMENT 'draft草稿(未配发售)/upcoming待发售/onsale发售中/soldout已售罄/off已下架';
```

状态映射说明：现有 `upcoming/onsale/soldout` 语义不变（C 端零感知）；新增 `draft`（管理端创建未发售）与 `off`（到期/手动下架）。C 端内容接口必须维持 `status IN ('upcoming','onsale','soldout')` 过滤，`draft/off` 不下发（改造点见 10.5）。

#### 4.1.2 `nft_blind_boxes`（盲盒扩展表）

盲盒库存即其藏品行的 `edition/sold/locked_quantity/reserved_count/airdropped_count/destroyed_count`（D-3 决策），本表仅补盲盒专属开关：

```sql
ALTER TABLE `nft_blind_boxes`
  ADD COLUMN `is_transferable` TINYINT(1) NOT NULL DEFAULT 1 COMMENT '盲盒是否可转赠 1=可 0=不可' AFTER `is_openable`,
  ADD COLUMN `is_resaleable`   TINYINT(1) NOT NULL DEFAULT 1 COMMENT '盲盒是否允许寄售（预留，P3 起用）' AFTER `is_transferable`;
```

#### 4.1.3 `nft_orders` / `nft_users` / `nft_resale_listings`

```sql
ALTER TABLE `nft_orders`
  MODIFY COLUMN `source` ENUM('release','market','priority','eligibility')
  NOT NULL DEFAULT 'release' COMMENT 'release公售/market市场/priority优先购/eligibility资格购（盲盒购买复用 release，凭 collectible 存在盲盒行区分）';

ALTER TABLE `nft_users`
  ADD COLUMN `is_blacklisted`  TINYINT(1) NOT NULL DEFAULT 0 COMMENT '是否黑名单 0=正常 1=黑名单' AFTER `status`,
  ADD COLUMN `blacklist_reason` VARCHAR(255) NULL DEFAULT NULL COMMENT '拉黑原因' AFTER `is_blacklisted`,
  ADD COLUMN `blacklist_at`     DATETIME(3) NULL DEFAULT NULL COMMENT '拉黑时间' AFTER `blacklist_reason`,
  ADD COLUMN `blacklist_by`     BIGINT UNSIGNED NULL DEFAULT NULL COMMENT '拉黑操作管理员ID' AFTER `blacklist_at`;

ALTER TABLE `nft_resale_listings`
  ADD COLUMN `is_system_delisted` TINYINT(1) NOT NULL DEFAULT 0 COMMENT '是否被系统强制下架 0=否 1=是' AFTER `status`,
  ADD COLUMN `system_delisted_at` DATETIME(3) NULL DEFAULT NULL COMMENT '系统下架时间' AFTER `is_system_delisted`,
  ADD COLUMN `delist_reason`      VARCHAR(255) NULL DEFAULT NULL COMMENT '下架原因' AFTER `system_delisted_at`;
```

`status` 枚举追加 `system_off`：


### 4.3 库存体系（核心闭环，所有模块共用）

#### 4.3.1 藏品库存公式

```
库存池（实时计算，不落库）
  = edition − sold − locked_quantity − reserved_count − airdropped_count − destroyed_count

流通量 circulate（落库，支付成功/空投发放时累加）
  = sold + airdropped_count   （合成/抽奖/盲盒产物属于"配额消耗"，计入 circulate 时同步扣减对应配额的 used_quantity）

实际可卖 = min( release_quantity − sold（若配置）, 库存池 )

库存守恒校验（藏品审计接口）
  edition = 库存池 + reserved_count + sold + airdropped_count + destroyed_count
  且用户持有(held+consigned+frozen) + consumed/transferred 统计 = circulate（按 source 分组核对）
```

`locked_quantity` 为瞬时值（待支付锁定，下单 +qty / 支付成功转 sold / 取消释放），纳入公式保证并发下不超发。

#### 4.3.2 配额规则

- 配额类型（全部可选）：优先购、活动空投、签到、注册、邀请、抽奖、其他；任何时间可配置（发售前/中/售罄后均可）。
- 新增/增量配额：`planned_quantity 增量 ≤ 当前库存池`，超发拦截并提示「库存池不足，当前库存池为 X」；配置成功 `reserved_count += 增量`（事务内与 CHECK 约束双保险）。
- 修改：`planned_quantity ≥ used_quantity`（已使用不可减）；减少的差额自动释放回库存池（`reserved_count 同步减`）。停用配额：释放全部未用部分。
- 活动实际发放（空投/签到/邀请/抽奖/盲盒奖品/合成产物）：动态校验对应配额 `used_quantity + 发放量 ≤ planned_quantity`，不足拦截「配额预留不足，当前剩余 X 份」，先到先得；同时原子更新 `used_quantity`。
- 数据库约束升级（替换原 CHECK）：

```sql
ALTER TABLE `nft_collectibles` DROP CHECK `chk_c_stock`;  -- 原约束名以实际库为准
ALTER TABLE `nft_collectibles` ADD CONSTRAINT `chk_c_stock` CHECK (
  `sold` + `locked_quantity` + `reserved_count` + `airdropped_count` + `destroyed_count` <= `edition`
  AND `circulate` <= `edition`
);
```

> MariaDB 10.2+ / MySQL 8.0+ 的 CHECK 对 UPDATE 生效；业务层仍在同一事务内做条件更新（`UPDATE ... WHERE sold+locked+reserved+airdropped+destroyed+qty <= edition`）防并发超发，与现有 C 端下单做法一致。

#### 4.3.3 盲盒库存公式（映射到藏品行，D-3）

```
盲盒库存池 = 该盲盒藏品行的 edition − sold − locked_quantity − reserved_count − airdropped_count − destroyed_count
盲盒流通量 = sold + airdropped_count
```

盲盒开启时（`BlindBoxes/open` 改造点）：

1. 用户盲盒资产置 `consumed`（现有逻辑保留）。
2. 命中子藏品后，实时校验子藏品库存池 > 0（原子条件更新其 `sold/circulate` 路径：开盒发放走 `airdropped_count +1, circulate +1` 并同步 `blind_box_items.quantity_distributed +1`）。
3. 库存不足自动降级空奖并写 `nft_risk_alerts`（alert_type=9，evidence 记录命中的 item），禁止超发。现有实现只校验 `quantity_distributed < quantity_limit`，本次改造补上库存池校验。

#### 4.3.4 强制回收的计数器回退

`nft_user_collectibles.source` 已有完整来源枚举，回收/撤销时按来源回退：

| 资产 source | 回退动作 | circulate |
| --- | --- | --- |
| purchase | `sold −1` | `−1` |
| airdrop | `airdropped_count −1` | `−1` |
| blindbox / lucky_draw / synthesis | 对应配额/活动 `used_quantity −1`（盲盒为 `quantity_distributed −1`） | `−1` |
| transfer | 追溯原始 source 同上处理 | `−1` |

回收前置校验：资产 `status = 'held'`（已被寄售/转赠冻结/消耗即拦截，提示具体原因）；盲盒已开启不可回收。

### 4.4 存量数据回填（迁移脚本内置，幂等）

```sql
-- 历史空投量回填：现有 circulate 与 sold 的差额即历史空投（开发库数据）
```

## 5. 核心业务闭环规则

> 本章为提示词第四章业务规则的落地版，所有规则后端为准、前端同步校验（提示友好，不作为安全边界）。

### 5.1 资格购（购买门槛系统，与优先购完全独立）

| 维度 | 资格购 | 优先购 |
| --- | --- | --- |
| 本质 | 购买**门槛/条件限制** | **时间优先**通道（公售前提前购买） |
| 是否占库存/配额 | 不占（纯门槛） | 不占（白名单资格次数） |
| 配置对象 | 条件组合（资格藏品/签到/邀请/手机号白名单） | 白名单（手机号/UID + 次数 + 有效期） |
| 相互关系 | 完全独立，同一藏品可同时配置两者，互不影响 | 同左 |
| 与每人限购 | 并存生效（per_user_limit 仍约束） | 并存生效 |

**配置规则**（藏品发售配置内 Switch 开启；条件可多选，组合方式 = 满足任一 / 满足全部）：

1. **资格藏品**：从**流通量 > 0** 的藏品中选择一个或多个（已发售、合成产物、抽奖所得、二级市场流通均算）；用户持有其中至少 1 个即满足。选择器仅展示 `circulate > 0` 的藏品。
2. **累计签到天数**：用户累计签到 ≥ 指定天数。
3. **累计邀请好友数**：累计邀请成功注册 ≥ 指定人数。
4. **额外资格手机号**：大文本框换行分隔，逐行校验必须为平台已注册用户，未注册直接拦截并提示行号与号码；白名单用户**无需满足其他条件**。
5. **有效期**：可配置开始/结束时间，过期自动失效。

未获得资格的用户在 C 端看到「未获得购买资格」提示，无法下单。

**购买判定流程**（`Orders/create` 后端校验，联动点 10.2）：

```
Step 1  用户是否持有该藏品的有效优先购资格？
        ├─ 是 → 可直接购买（优先购覆盖资格购限制）
        └─ 否 → Step 2
Step 2  该藏品是否开启资格购？
        ├─ 否 → 正常购买（无门槛）
        └─ 是 → Step 3
Step 3  条件判定（组合方式 = 任一 / 全部）
        A. 额外手机号白名单命中
        B. 持有资格藏品（至少 1 个）
        C. 累计签到天数 ≥ 要求
        D. 累计邀请人数 ≥ 要求
        └─ 不满足 → 拦截「未获得购买资格」
```

关键规则：优先购不参与资格购（白名单是唯一"无条件"通道）；资格购只是门槛，购买仍受每人限购约束；资格藏品必须流通量 > 0；资格购订单 `source = 'eligibility'`（4.1.3 已扩枚举）。

### 5.2 优先购（时间优先通道，全链路）

- **配置**：每藏品独立配置活动（时间窗必须早于或重叠藏品发售时间）；白名单记录手机号/UID、`max_quantity`、`used_quantity`、`expires_at`（精确到时分秒）。
- **购买**（联动点 10.2）：有效资格 = `expires_at > now` 且 `used_quantity < max_quantity` 且活动窗口内；购买成功 `used_quantity + 1`（原子条件 UPDATE 防并发超用），订单 `source = 'priority'`。
- **台账**：用户详情页展示「优先购资格台账」（有效 / 过期 / 已用完三组，接口 `/users/:id/priority-qualifications`）。
- **清理**：支持批量清理过期资格（二次确认 + 密码，接口 `/marketing/priority/cleanup`）。

### 5.3 寄售开关与转赠开关（完全独立，互不干扰）

| 开关 | 字段 | 开启 | 关闭 |
| --- | --- | --- | --- |
| 寄售开关（藏品级） | `is_resaleable` | 持有者可挂单寄售 | 该藏品**全部在售挂单自动强制下架**（`status = 'system_off'`），用户无法重新上架 |
| 转赠开关（藏品/盲盒级） | `is_transferable` | 转赠入口可用 | C 端「转赠」按钮隐藏/置灰；**已发起待确认的转赠不受影响**，无需处理存量记录 |

寄售细则：

- 仅藏品状态为「已售罄 / 发售中」时可切换；关闭需二次确认 + 原因 + 密码，写审计日志。
- **价格管控**（`resale_price_mode`）：0 不限价 = 用户自由定价（仅保留全局单笔最大金额校验）；1 限价 = 挂单价必须落在 `[resale_price_min, resale_price_max]` 闭区间（C 端挂单接口校验，联动点 10.3）。
- 市场监控列表增加「限价状态」列（限价 / 不限价）；开关与限价变更全部写审计日志。

### 5.4 奖励类型统一

全平台活动奖励下拉统一六类（较提示词增加司南币，见 D-4），各活动配置面板按类型弹对应表单：

| reward_type | 配置面板内容 | 实际发放动态校验（先到先得） |
| --- | --- | --- |
| `collectible` 藏品 | 选择已创建藏品 + 数量（计划上限） | 配额 `used + 发放量 ≤ planned`，或库存池充足 |
| `priority_qualification` 优先购资格 | 选择优先购活动 + 资格数量 + 有效期 | 活动存在且未结束 |
| `eligibility_qualification` 资格购资格 | 选择目标藏品 + 资格数量 + 有效期（精确到时分秒） | 目标藏品存在 |
| `draw_chance` 抽奖次数 | 次数 | — |
| `blindbox` 盲盒 | 选择已创建盲盒 + 数量（计划上限） | 盲盒库存池充足 |
| `points` 司南币（D-4 保留） | 金额 | — |

- **计划上限与实际发放脱钩**：配置的数量是计划上限，实际发放时动态校验配额预留/库存池，不足拦截「配额预留不足，当前剩余 X 份」或按活动规则降级（空奖）。
- 所有批量发放（空投、签到、邀请、抽奖、盲盒奖励、快捷补偿）生成完整发放记录台账，支持按活动/用户/时间筛选导出。

#### 5.4.1 抽奖奖项概率闭环

- 奖项池支持多奖项，每个奖项独立配置：名称、类型、内容、中奖概率（0.0001~100，4 位小数）、数量（计划上限）、状态。
- 保存校验：**非空奖概率之和 ≤ 100%**，超出拦截「中奖概率总和不得超过 100%，当前合计 X%」；空奖概率 = 100% − 非空奖合计。
- 实际抽奖双保险：预生成随机数按概率命中奖项 → 校验该奖项剩余计划量与对应库存/配额 → 不足自动降级空奖并写 `nft_risk_alerts`（禁止超发）。

#### 5.4.2 盲盒子藏品概率闭环

- 每个盲盒关联 2~N 个子藏品，每个独立配置：子藏品（从库存池 > 0 或流通量 > 0 的藏品中选择）、概率（0.0001~100，4 位小数）、计划数量。
- 保存校验：概率之和 ≤ 100%（大于拦截「子藏品概率总和不得超过 100%，当前合计 X%」）；小于 100% 的差额视为空奖。
- **不预先冻结子藏品库存**；开盒时按概率命中后实时校验子藏品库存池（4.3.3），不足自动降级空奖 + 告警，禁止超发。
- 开启记录：盲盒 ID、用户、命中子藏品、发放状态、时间；管理端配置界面必须可视化展示概率分布（进度条/饼图预览）。

### 5.5 撤销 / 回收边界校验

| 操作 | 前置校验 | 拦截提示（必须明确原因，禁止静默失败） |
| --- | --- | --- |
| 强制回收藏品 | 资产 `status = 'held'` 且未二次流转（转赠/寄售/合成消耗/盲盒消耗） | 「该藏品已发生二次流转，无法回收」/「该藏品正在寄售/转赠冻结中，无法回收」 |
| 强制回收盲盒 | 该盲盒资产未被开启（`consumed` 即拦截） | 「该盲盒已被开启，无法回收」 |
| 撤销转赠 | 仅「已完成」转赠可撤销；接收方当前仍持有（`held`）且未再次转赠/寄售/合成/消耗/开启 | 「接收方已对该藏品/盲盒进行其他操作，无法撤销」 |
| 撤销空投 | 同上，校验接收方当前持有状态 | 同上 |

回收/撤销成功后按 4.3.4 回退藏品计数器。

- **保留内容**：管理员账号、藏品元数据（`sold/locked_quantity/reserved_count/airdropped_count/destroyed_count/circulate` 计数器归零，库存池恢复为发行总量）、盲盒元数据（同上 + `blind_box_items.quantity_distributed` 归零）、CMS 内容、系统配置。
- 执行前自动全库备份（记录 `backup_path`）；操作人/IP/时间/原因写审计日志与 `nft_platform_cleanup_logs`；权限仅超级管理员。

### 5.8 审计日志全覆盖

- 覆盖范围：全部后台写操作、批量导入、空投发放、活动配置、白名单操作、实名完整查看、强制回收、撤销转赠、平台清库、盲盒/概率配置修改。

## 6. 状态流转

### 6.1 藏品状态机

状态枚举沿用 4.1.1 扩展后的 `draft / upcoming / onsale / soldout / off`（现有 `upcoming/onsale/soldout` 语义不变，C 端零感知）：

```
draft(草稿)
  │ [配置发售并上架] ──────────────► upcoming(待发售，发售时间未到)
  │ [无关联时物理删除]                 │ [到点自动]
  │                                   ▼
  │                                onsale(发售中)
  │                                   ├─ [库存池=0] ────► soldout(已售罄)
  │                                   ├─ [到期/手动下架] ► off(已下架)
  │                                   └─ [强制售罄] ─────► soldout(已售罄)
  │                                        ▲                  │
  │                                        │  [重新上架，≤库存池，二次确认+密码]
  │                                        └────── off/soldout ┘
```

| 状态 | 允许操作 | 禁止 |
| --- | --- | --- |
| draft | 编辑基础信息、删除（无关联）、发售配置、资格购配置、配额配置 | 售卖、C 端可见 |
| upcoming | 修改发售配置、配额配置 | 售卖、编辑基础信息 |
| onsale | 配额、独立空投、销毁、强制售罄、下架、寄售/价格管控 | 编辑基础信息、删除 |
| soldout | 重新上架（≤库存池）、配额、独立空投、销毁、寄售/价格管控 | 编辑、删除 |
| off | 重新上架（≤库存池）、配额配置、（盲盒行可修改子藏品概率） | 售卖 |

`upcoming → onsale` 的到点切换：不依赖定时任务硬刷状态，C 端查询时以 `onsale_at` 时间判定为主（现有实现），管理端列表展示时同步计算；强制售罄不清零任何计数器，仅停止发售（剩余留在库存池）。

### 6.2 盲盒状态机

盲盒行即藏品行（D-3），状态机与 6.1 完全一致，差异点：

```
盲盒专属差异：
  draft/off ──► 可配置/修改子藏品与概率（发售中禁止改概率，需先下架）
  soldout   ──► 可独立空投（扣盲盒库存池）、可销毁
  已开启的盲盒资产（consumed）──► 不可回收（5.5）
```

| 状态 | 允许操作 | 禁止 |
| --- | --- | --- |
| draft | 编辑、上传盲盒图、配置子藏品与概率、删除（无关联） | 售卖 |
| upcoming / onsale | 售卖 | 修改子藏品概率（需先下架） |
| soldout | 重新上架、独立空投、销毁 | 编辑 |
| off | 重新上架、修改子藏品与概率 | 售卖 |

### 7.2 实现方式

- **后端**：`AdminAuth` 中间件解析管理员 JWT（claim：`typ=admin, aid, role`）→ `AdminPermission` 中间件按路由标注权限码校验；权限码映射 P0 期由 `PermissionMap` 静态维护，P3 期升级为 `nft_admin_role_permissions` 库表驱动（支持自定义角色）。
- **前端**：登录后 `/auth/me` 返回 `permissions` 数组 → Pinia `permission` store → `router.addRoute` 动态注册路由 + `v-permission="['xxx']"` 自定义指令控制按钮显隐。
- **数据权限**：客服角色后端按角色过滤响应字段（仅脱敏信息）；超管之外角色不返回 `is_realname` 之外的实名明文字段。
- 401 跳转登录页；403 弹窗提示无权限；角色不可删除自己、不可操作同级及以上账号。

### 7.3 权限码清单

权限码全集以第 8 章各模块接口表「权限码」列为准（命名规则 `模块:动作`，如 `collectible:release`、`marketing:priority:whitelist`）。统计：19 个模块分组约 96 个权限码，其中运营角色约 41 个、财务约 14 个、风控约 18 个、客服约 7 个。

## 8. 后端接口设计

### 8.1 接口通用规范

- **BaseURL**：`/admin/api/v1`；**认证**：Header `Authorization: Bearer <admin_jwt>`（管理员 JWT，与 C 端用户 JWT 密钥隔离）。
- **响应格式**：沿用现有 `{code: 0, data, message}`（D-2），`code === 0` 为成功；401 未登录、403 无权限/密码错误、409 业务冲突（库存/配额不足、状态不允许）、422 参数错误、500 服务器错误。
- **分页**：`page`（默认 1）/ `page_size`（默认 20，最大 100），列表响应统一 `{list, total}`。
- **时间**：ISO 8601；**金额**：字符串两位小数（后端 BCMath，前端 Decimal.js）。
- **高风险接口**：请求体必含 `password`（当前管理员登录密码），后端 `password_verify` 校验失败返回 403 并写安全事件；列表见 11.1。
- 所有写操作经 `AuditLogService` 记录 before/after；导出接口后端流式下载（CSV/XLSX），禁止前端拼接大数据量。

## 11. 高风险操作与硬性约束

### 11.1 高风险操作统一规范

前端统一走 `PasswordVerify` 弹窗（3.3 视觉规范），后端统一校验请求体 `password` 字段：

| 操作 | 确认流程 | 额外校验 |
| --- | --- | --- |
| 强制回收藏品 | 二次弹窗 + 原因 + 密码 | 校验二次流转 |
| 强制回收盲盒 | 二次弹窗 + 原因 + 密码 | 校验是否已开启 |
| 独立空投藏品 | 二次弹窗 + 密码 | ≤ 库存池，手机号已注册 |
| 独立空投盲盒 | 二次弹窗 + 密码 | ≤ 盲盒库存池，手机号已注册 |
| 关闭寄售 | 二次弹窗 + 原因 + 密码 | 自动下架对应藏品所有挂单 |
| 撤销转赠 | 二次弹窗 + 原因 + 密码 | 校验接收方当前持有 |
| 撤销空投 | 二次弹窗 + 原因 + 密码 | 校验接收方当前持有 |
| 删除藏品 | 二次弹窗 + 密码 | 仅草稿无关联 |
| 删除盲盒 | 二次弹窗 + 密码 | 仅草稿无关联 |
| 平台清库 | 四重确认（5.7） | 自动备份 |
| 强制售罄藏品 | 二次弹窗 + 原因 + 密码 | 不清零，发售停止，剩余回库存池 |
| 强制售罄盲盒 | 二次弹窗 + 原因 + 密码 | 不清零，发售停止，剩余回盲盒库存池 |
| 重新上架藏品 | 二次弹窗 + 密码 | ≤ 库存池 |
| 重新上架盲盒 | 二次弹窗 + 密码 | ≤ 盲盒库存池 |
| 销毁藏品库存 | 二次弹窗 + 数量 + 密码 | ≤ 库存池 |
| 销毁盲盒库存 | 二次弹窗 + 数量 + 密码 | ≤ 盲盒库存池 |
| 配额修改 | 二次弹窗 + 密码 | 已使用不可减 |
| 盲盒子藏品概率修改 | 二次弹窗 + 密码 | 概率总和 ≤ 100% |
| 实名完整查看 | 二次弹窗 + 密码 | 写入审计日志 |
| 退款审批 | 审批流程 + 密码 | 金额校验 |
| 敏感操作审批 | 发起审批 + 审批人审核 + 密码 | 数据快照 |
